# The Wandering City｜MVP 技术方案

## 1. 目标与实施基线

本方案对应《产品设计文档-MVP.md》，采用 Unity + C# 实现第三人称单机冒险游戏，交付约 20～30 分钟的探索、战斗、奖励与升级闭环。

暂以 Windows PC、键鼠操作为首发开发基线；这是实施假设，正式创建工程前需确认。美术建议采用风格化原创设计，先以灰盒和风格一致的占位资产验证玩法，再逐步替换正式资源。

MVP 使用一块小型手工地图，包含出生据点、树林、矿区和敌人营地。采用固定地形，不引入无限地图、地形挖掘、联网服务或复杂大世界流式加载。

## 2. 技术栈

| 层面 | 选择 | 用途 |
| --- | --- | --- |
| 引擎 | Unity 6，建项时选择受支持的稳定版本并锁定 | 场景编辑、运行与 Windows 构建 |
| 语言 | C# | 玩法规则、角色与世界交互 |
| 渲染 | URP | 风格化场景、材质、光照与基础特效 |
| 输入 | Unity Input System | 移动、镜头、攻击、闪避、交互与菜单输入 |
| 角色与镜头 | CharacterController + Cinemachine | 角色碰撞移动、第三人称跟随与镜头避障 |
| 动画 | Animator | 移动、攻击、闪避、受伤与死亡表现 |
| 敌人导航 | AI Navigation / NavMesh | 静态地图中的巡逻与追击 |
| 游戏界面 | uGUI + TextMeshPro | HUD、背包、工作台、建造与暂停菜单 |
| 数据 | ScriptableObject 配置 + 普通 C# 运行时状态 | 物品、配方、武器、敌人与目标配置 |
| 存档 | 本地 JSON 文件 | 版本化保存与恢复单机进度 |
| 素材与版本管理 | Blender、Git、Git LFS | 模型处理、代码与大型二进制素材管理 |
| 测试 | Unity Test Framework | Edit Mode 规则测试与 Play Mode 场景测试 |

具体编辑器和包版本在建项时验证兼容性，提交版本记录与包锁定文件。开发期间不自动升级引擎；升级必须单独验证并提交。

当前不需要后端、数据库、账号或云存档。现有 `demo/` 保留为界面和流程参考，正式游戏建议放在独立的 `game/` Unity 工程中；复用玩法规则与体验结论，Unity 中重新实现场景和交互。

## 3. 工程组织与模块边界

建议游戏自有资源统一放在 `Assets/_Game/` 下，按 Scripts、Scenes、Prefabs、Data、Art、Audio、UI、Tests 分类。代码按 Player、Combat、World、Inventory、Crafting、Building、Progression、Save、UI 划分模块。

采用简单的 GameObject / MonoBehaviour 组件结构。背包、配方、升级、奖励与存档数据转换尽量保持为独立 C# 逻辑，便于脱离场景测试。UI 发起操作并显示结果，不直接修改资源数量；各系统通过明确的方法和必要的事件协作，避免引入大型通用框架。

ScriptableObject 只保存设计配置，玩家数量、进度和状态使用独立运行时对象，避免游玩时改写配置资产。

场景先划分为启动场景和游戏地图场景。地图内直接布置三个兴趣点及据点，通过地标、道路和奖励位置组织探索。MVP 不先做分区加载或程序化地图。

## 4. 核心功能实现

### 4.1 角色、镜头与战斗

- 角色采用相对镜头方向移动，自行处理重力、跳跃、接地、坡面与台阶。优先验证转向、加减速、跳跃落地和狭窄区域碰撞。
- 镜头支持鼠标旋转、俯仰限制和障碍物避让；打开背包或暂停菜单时切换输入模式及鼠标锁定状态。
- 采用移动、攻击、闪避、受伤、死亡等明确状态，控制动作互斥与允许的打断。首版由代码驱动位移，动画负责表现，避免两套位移同时生效。
- 普通攻击使用配置化的准备、命中和收招阶段，在命中窗口进行近战范围检测。同一次攻击对同一目标只结算一次，穿墙命中需要遮挡检查。
- 闪避包含配置化的位移、持续时间、冷却和短暂无敌窗口。伤害逻辑统一检查状态，死亡后禁止继续攻击或受伤结算。
- 受击反馈结合动画、音效、特效和适度镜头反馈。具体节奏通过实际游玩调整。

### 4.2 敌人与世界交互

一种近战敌人采用有限状态机：巡逻、追击、攻击、返回、死亡。使用视距、视线遮挡、攻击距离和追击边界决定切换，限制攻击频率；无法到达玩家时应停止无效攻击并尝试返回。

统一交互接口覆盖拾取、宝箱、资源点和工作台。根据距离与视线选取目标并显示提示；资源变化和奖励领取在逻辑层再次校验，避免连续输入重复领取。资源点只改变自身可采集状态，不改变地形。

为一次性奖励、关键遭遇和可持久化世界对象分配稳定 ID，不使用运行时实例 ID 作为存档标识。MVP 建议已击败敌人和已采集资源在保存后保持状态；刷新机制后续独立评估。关键材料在敌人营地完成后由可持久化奖励点领取，避免掉落丢失导致无法升级。

### 4.3 背包、制作、升级与目标

物品使用稳定 ID，配置名称、图标、类型和堆叠上限。背包负责数量和容量校验；快捷栏引用物品 ID，使用时检查剩余数量。

拾取、制作、升级、建造和回收均采用“完整校验后一次提交”的资源操作。材料不足、容量不足或状态非法时不扣除任何资源，也不生成结果。恢复道具校验生命状态，死亡时不可使用。

引导目标读取实际进度，可支持玩家提前探索或领取奖励，避免严格顺序导致卡关。武器升级限定为 MVP 的一次升级，并明确体现伤害提升。

### 4.4 轻量建造

在据点限定区域内放置地板、墙体和屋顶预制件，采用网格或连接点吸附，支持旋转、预览和有效性提示。放置前检查区域、支撑与碰撞，防止重叠、悬空或覆盖玩家及关键交互点。

MVP 建议禁止在敌人活动路线和关键通路上建造，避免运行时导航重建。拆除时检查依赖关系，有依赖模块时提示先拆除上层；回收数量由配置决定，并先检查背包容量。放置、拆除与回收必须和资源结算保持一致。

## 5. 存档与恢复

使用 `Application.persistentDataPath` 下的单槽 JSON 存档，包含存档格式版本及以下内容：

- 角色位置、朝向、生命值及必要状态。
- 背包、快捷栏与武器升级等级。
- 目标进度和一次性奖励领取记录。
- 关键遭遇、敌人和资源点的持久化状态。
- 据点建筑的实例 ID、预制件配置 ID、位置与旋转。

临时战斗动作不直接保存；加载时恢复到可控状态，敌人恢复为非攻击状态。角色存档位置非法或存档时已死亡时，回到据点安全位置。死亡重生保留背包和进度，不扣除物品。

提供暂停菜单手动保存，并在奖励领取、制作、升级、建造和重生等关键操作完成后自动保存。收集完整快照并串行写入，先写临时文件，再替换主文件并保留上一份备份，避免并发写入与中断造成主档损坏。

加载时校验格式、配置 ID 和关键字段；主档损坏时尝试备份。未知版本或主备份均不可用时明确提示，不静默覆盖旧档。存档结构变更时提供迁移或明确的不兼容处理，并补充测试。

## 6. 开发顺序与阶段出口

| 阶段 | 交付内容 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1. 基础操作 | 灰盒场地、第三人称移动、镜头、跳跃 | 常规地形移动和镜头稳定，基础操作可接受 |
| 2. 战斗切片 | 一种敌人、攻击、闪避、伤害与重生 | 能重复完成一次遭遇，无重复伤害或流程阻断 |
| 3. 冒险闭环 | 小地图、采集、背包、制作、奖励、升级、目标与存档 | 从据点出发到完成升级的流程可玩，重载进度一致 |
| 4. 建造与打磨 | 少量建筑模块、回收、正式界面、音效与视觉反馈 | 完整 20～30 分钟体验通过验收 |

优先投入角色手感、动画衔接和兴趣点布局。范围超出预期时先减少建筑模块、配方和装饰内容，保留探索战斗与成长闭环。

## 7. 测试、性能与交付

详细用例见《技术方案-MVP-验证清单.md》。规则层通过 Edit Mode 自动测试覆盖资源守恒、操作失败不修改状态、奖励幂等、升级限制与存档往返；Play Mode 覆盖角色和敌人状态、攻击命中、交互、建筑放置及场景恢复。

镜头舒适度、操作手感、奖励可见性和地图探索节奏需要人工游玩验证。现有前端 Demo 的测试继续保留，但不能代替 Unity 的测试和 Windows 构建验证。

性能目标暂定为约定参考 PC 上 1080p、常规游玩稳定接近 60 FPS；建项时补充参考硬件和画质档位再作为验收门槛。使用 Unity Profiler 检查实际构建中的帧耗时、内存及 GC，优先控制可见物体、阴影、材质和频繁分配，依据测量结果优化。

每次改动同步编写或更新相关测试与验证记录，交付前运行适用的自动测试和人工验证，并创建对应 Git commit。大型二进制素材纳入 Git LFS；Unity 的 `.meta` 文件随资产提交，Library、Temp、Logs 和本地构建产物不纳入版本控制。

## 8. 建项前需确认

1. 首发是否采用 Windows PC，以及最低参考硬件。
2. 美术方向、可用资产来源和授权情况。
3. Unity 编辑器与包的具体锁定版本。

本方案不预估工期，不包含多人、攀爬、滑翔、元素反应、动态天气或大型建造系统；后续扩展应在 MVP 验证后单独评估。
